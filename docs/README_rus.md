# fm — модульный файловый менеджер с локальной ИИ-сортировкой

[Не понятно? Перевод на "пацанский"](прочитайменя.md)

Файловый менеджер для Linux, собранный как «конструктор»: каждый модуль независим,
заменяем и общается с остальными через небольшой явный интерфейс. Обход директорий сделан
через сырые системные вызовы (без обращения к `ls`/`find`/`stat`); классификация через ИИ,
эмбеддинги и сортировка по естественному языку работают полностью локально через
[Ollama](https://ollama.com), и ни один другой модуль не блокируется, если ИИ недоступен.

Границы модулей (полный список интерфейсов — в `docs/architecture.md`):

| Крейт         | Ответственность                                                       | Зависит от            |
|---------------|-------------------------------------------------------------------------|-----------------------|
| `fm-types`    | Общие типы данных + типы AI-протокола                                   | —                     |
| `fm-config`   | TOML-конфиг, общий с Python-движком                                      | —                     |
| `fm-core`     | Обход директорий через сырые syscalls, кэш метаданных, MIME/хэш, пул потоков | `fm-types`* (на деле нет — см. примечание) |
| `fm-db`       | Трейт `Database` + реализация SQLite, миграции                           | `fm-types`, `fm-config` |
| `fm-sorter`   | Шаблоны, план/выполнение/откат, разрешение конфликтов                    | `fm-types`            |
| `fm-watcher`  | Рекурсивный inotify-наблюдатель с дебаунсингом батчей                    | `fm-core`             |
| `fm-ai`       | Блокирующий клиент для Unix-socket протокола AI-движка                   | `fm-types`            |
| `fm-app`      | Связывает всё вместе; единственный межмодульный крейт                    | все вышеперечисленные |
| `fm-cli`      | Парсинг аргументов + вывод; вызывает только `fm-app`                     | `fm-app`              |
| `ai-engine`   | Python asyncio-сервис: извлечение контента, мост к Ollama, промпт→правила | (только stdlib)      |

`fm-core` на практике не зависит от `fm-types` (у него свои `Meta`/`FileKind`, потому что
это понятия *файловой системы*, а не индекса) — это сделано намеренно: обходчик должен
оставаться рабочим, даже если типы индекса/ИИ поменяют форму.

## Сборка

Нужен Rust ≥ 1.75 и Python ≥ 3.11.

```bash
cargo build --release                 # собирает fm-types .. fm-cli; бинарник в target/release/fm
cd ai-engine && pip install -e .      # или: pip install -e '.[pdf,audio]' для извлечения из PDF/аудио
```

## Запуск

```bash
# 1. запустить Ollama (нативная установка, либо `docker compose -f docker/docker-compose.yml up -d ollama`)
ollama pull llama3
ollama pull llava
ollama pull nomic-embed-text

# 2. запустить AI-движок (читает ~/.config/fm/config.toml, или $FM_CONFIG)
cp config/config.example.toml ~/.config/fm/config.toml
python -m aiengine &

# 3. пользоваться CLI — всё работает даже до завершения шагов 1/2; ИИ-функции деградируют мягко
fm index ~/Documents
fm analyze ~/Documents
fm find --category Finance
fm search "налоговые документы за прошлый год"
fm rules
fm sort ~/Documents --rule by-type                 # сухой прогон (без изменений)
fm sort ~/Documents --rule by-type --apply
fm sort ~/Pictures --prompt "разложи фото по годам и событиям" --apply
fm undo
fm watch ~/Documents
fm status
```

Ещё нет Ollama, или просто хочется прощупать систему? `python -m aiengine --mock` запускает
детерминированный офлайн-бэкенд (категоризация по ключевым словам, эмбеддинги на хэшированном
bag-of-words) — он же используется в интеграционных тестах, и удобен, чтобы погонять
систему без скачивания моделей.

## Тестирование

```bash
cargo test --workspace                                 # юнит + интеграционные тесты (Rust)
cd ai-engine && python -m unittest discover -s tests    # юнит + end-to-end тесты (Python)
```

`crates/fm-app/tests/integration_ai.rs` — интеграционный набор Core+DB+AI+Sorter: он
поднимает *настоящий* Python-движок (бэкенд `--mock`, без сети) как дочерний процесс и
гоняет через реальный Unix-socket протокол: индексация, инкрементальный повторный анализ,
семантический поиск, сортировка по промпту, применение и откат — всё целиком.

## Производительность

Методология и шаги воспроизведения бенчмарка обхода директорий против
`ls -la --color=never` — в `bench/README.md` (цель: не более чем на 10-15% медленнее `ls`
на директории со 100 000 файлов; измеренный результат в песочнице CI здесь — примерно
в 2.4 раза *быстрее*, в основном потому что GNU `ls -l` резолвит каждый uid/gid в имя
через NSS, а fm-core — нет).

## Мягкая деградация при отсутствии ИИ

`fm-app::App::ai_available()` пингует движок (с коротким кэшированием результата) перед
любым ИИ-зависимым вызовом. Когда движок недоступен: `fm index`, `fm ls`, `fm find`,
встроенная `fm sort --rule by-type/by-date/by-ext`, `fm undo` и `fm watch` (без
`auto_analyze`) продолжают работать как обычно. `fm analyze`, `fm search` и
`fm sort --prompt` (или `--rule by-category` до того, как что-либо проанализировано)
возвращают понятную ошибку `AiUnavailable` с подсказкой, вместо того чтобы зависать
или падать.

## Расширение проекта

- **Новые наборы правил**: добавь JSON `RuleSet` через `fm sort --prompt "..." --save-as my-rule`
  (ИИ сам распарсит и провалидирует), либо напиши его напрямую и сделай `INSERT` в
  `sort_rules` — `fm-sorter` в любом случае видит только уже провалидированную структуру
  `RuleSet`.
- **Бэкенд PostgreSQL**: реализуй `fm_db::Database` для него и добавь ветку в `match` внутри
  `fm_db::open`; все остальные крейты уже общаются с `dyn Database`, а не напрямую с SQLite.
- **Новый AI-бэкенд / модель**: реализуй `aiengine.backend.Backend`; `handlers.Engine` и
  уровень RPC не привязаны к конкретному бэкенду (минимальная форма — смотри `MockBackend`).
- **GUI**: вызывай `fm_app::App` напрямую, так же как это делает `fm-cli` — парсинг
  аргументов командной строки для этого не нужен.
